# Dependabot lockfix: regenerate Gradle dependency-verification metadata

**Goal.** Dependabot cannot run Gradle, so in a repo with Gradle dependency
verification on (`gradle/verification-metadata.xml`), every Gradle bump arrives
with stale checksums and CI fails `Dependency verification failed` until a
human regenerates the file on a Mac. nullnet-app/allotmint has needed that by
hand on every Gradle dependabot PR in its history (latest: allotmint#384).
Extend the existing `reusable-dependabot-lockfix.yml` so it can regenerate the
file on ubuntu and push it back, without weakening its security model.

**Background established before this plan (do not re-litigate):**

- A ubuntu `--write-verification-metadata sha256` run records every checksum CI
  needs EXCEPT host-tool artifacts published per OS: `aapt2` (classifiers
  `linux`/`osx`), `kotlin-native-prebuilt` (`linux-x86_64`/`macos-aarch64`) and
  the Kotlin/JS `org.nodejs:node` distribution (`linux-x64`/`darwin-arm64`).
- iOS klibs are NOT a gap: allotmint#393 adds `-Pallotmint.iosKlibs`, which
  declares the iOS targets on Linux. Verified on ubuntu: all 8 current
  kotlinx-serialization iOS klib checksums came back byte-identical to the
  Mac-generated ones.
- Without that property CI is unaffected; with it a regen pulls the ~850 MB
  Kotlin/Native toolchain, so it belongs ONLY in the lockfix command.
- In allotmint's metadata, existing host-tool entries look like this (artifact
  name has no `v`; origin strings are free text):

  ```xml
  <component group="com.android.tools.build" name="aapt2" version="9.5.0-16666295">
     <artifact name="aapt2-9.5.0-16666295-linux.jar">
        <sha256 value="fa10…" origin="Computed from Google Maven; sha1 matches the published .sha1. CI's ubuntu lanes need the linux classifier"/>
     </artifact>
     <artifact name="aapt2-9.5.0-16666295-osx.jar">
        <sha256 value="a43d…" origin="Generated by Gradle"/>
     </artifact>
  </component>
  <component group="org.jetbrains.kotlin" name="kotlin-native-prebuilt" version="2.4.21">
     <artifact name="kotlin-native-prebuilt-2.4.21-macos-aarch64.tar.gz"> …
  <component group="org.nodejs" name="node" version="24.10.0">
     <artifact name="node-24.10.0-darwin-arm64.tar.gz"> …
     <artifact name="node-24.10.0-linux-x64.tar.gz"> …
  ```

**Security model to preserve** (read the header comment of
`.github/workflows/reusable-dependabot-lockfix.yml` and `scripts/lockfix.test.sh`):
the `lockfix` job runs PR-controlled code, holds no secret, and hands over only
a patch; the `push` job holds the PAT, runs no PR code, and treats the patch as
attacker-shaped data. Every change below keeps that split, and every new input
is optional with a default that keeps today's behaviour, because every
consumer stub calls the reusable `@main`.

## Task T1 — `append-only-paths`: the push job refuses a patch that removes or changes a line

A regenerated verification file only ever ADDS checksums. A removed or changed
checksum for a coordinate we already list is exactly the tampering signal
dependency verification exists to catch, so it must never be auto-pushed.

1. Add an optional `workflow_call` input `append-only-paths` (string,
   space-separated pathspecs, default `""` = no check) to
   `reusable-dependabot-lockfix.yml`, passed into the `Commit and push drift`
   step as an env var.
2. In that step, after `git apply --index` and the existing confinement and
   mode checks: for every staged file matching an append-only pathspec, if
   `git diff --cached` shows ANY removed line (a `-` line that is not the `---`
   header), print `::error::` naming the file and the offending lines, and exit
   non-zero before committing. A file that is newly created at such a path is
   fine (all additions). Implement in bash inside the step, as the other checks
   are.
3. Tests in `scripts/lockfix.test.sh` (new cases, same fixture style; the
   `run_push` helper will need an `APPEND_ONLY` env passthrough):
   - pure additions to an append-only path are committed and pushed;
   - a patch that changes one existing line of an append-only path is refused
     and nothing is pushed, with an error naming the path;
   - a patch that deletes a line of an append-only path is refused;
   - with `append-only-paths` empty, a changing patch to the same file still
     pushes (backward compatibility);
   - a non-append-only path in the same patch may still change lines.
   Extend the structure assertion so the input exists and defaults to empty.
4. Document the input in the reusable's header comment (why: tampering signal).

## Task T2 — `host-tool-checksums`: add the other-OS variants of host-tool artifacts

A ubuntu regen records only the Linux variant of OS-specific host tools; the
macOS variants are needed by the iOS lane (self-hosted Mac) and by local
development. Add them by downloading and checksumming, never by running them.

1. Add an optional boolean `workflow_call` input `host-tool-checksums`
   (default `false`), and a step in the `lockfix` job that runs only when it is
   true, AFTER `Regenerate lockfiles` and BEFORE `Package lockfile drift`,
   operating on `gradle/verification-metadata.xml`. Keep the logic inline in
   the YAML step (bash, may call `python3` for XML-safe editing) so
   `lockfix.test.sh` can extract and run it like the other steps.
2. Behaviour:
   - Consider ONLY components whose `<component>` block is new or changed
     relative to `git show HEAD:gradle/verification-metadata.xml` (so a regen
     does not backfill every historic version).
   - Fixed table — no other coordinates are ever fetched:

     | group:name | classifiers | URL of artifact | verify against |
     |---|---|---|---|
     | `com.android.tools.build:aapt2` | `linux`, `osx` (`.jar`) | `https://dl.google.com/dl/android/maven2/com/android/tools/build/aapt2/<v>/aapt2-<v>-<c>.jar` | `<url>.sha1` |
     | `org.jetbrains.kotlin:kotlin-native-prebuilt` | `linux-x86_64`, `macos-aarch64` (`.tar.gz`) | `https://repo1.maven.org/maven2/org/jetbrains/kotlin/kotlin-native-prebuilt/<v>/kotlin-native-prebuilt-<v>-<c>.tar.gz` | `<url>.sha1` |
     | `org.nodejs:node` | `linux-x64`, `darwin-arm64` (`.tar.gz`) | `https://nodejs.org/dist/v<v>/node-v<v>-<c>.tar.gz` | that line of `https://nodejs.org/dist/v<v>/SHASUMS256.txt` |

     Artifact names written into the XML follow the existing entries:
     `aapt2-<v>-<c>.jar`, `kotlin-native-prebuilt-<v>-<c>.tar.gz`,
     `node-<v>-<c>.tar.gz` (no `v`).
   - For each such component, for each classifier in the table whose
     `<artifact>` is missing: validate `<v>` against `^[0-9A-Za-z][0-9A-Za-z.+-]*$`
     (refuse anything else), download with `curl -fsSL --proto '=https'`,
     compute sha256, and cross-check against the published sha1 (or the
     SHASUMS256 line). On mismatch or download failure: `::warning::` and skip
     that artifact (the PR stays red for a human, which is today's behaviour);
     never write an unverified checksum.
   - Insert `<artifact name="…"><sha256 value="…" origin="…"/></artifact>` into
     that component, keeping artifacts sorted by name and the file's existing
     indentation, with an origin like `"Computed by dependabot lockfix from
     <host>; matches the published .sha1"`. The result must be pure additions
     (T1's guard will be applied to this file).
   - Never touch any other part of the file.
3. Tests in `scripts/lockfix.test.sh`, fully offline: stub `curl` on PATH so it
   serves fixture bytes from a temp dir for the table's URLs and fails for
   anything else. Cases:
   - a new aapt2 component with only the linux artifact gains the osx artifact
     with the right sha256, sorted, and the diff vs HEAD has no removed lines;
   - a new node component gains darwin-arm64 from a fixture SHASUMS256.txt;
   - a published-hash mismatch writes nothing for that artifact and warns;
   - an unchanged (already-in-HEAD) component missing a variant is NOT touched;
   - a version that fails the regex is refused without any curl call;
   - with the input false, the step does not run (structure assertion).
4. Document in the reusable's header comment: what it fetches, that it runs no
   downloaded code, and that its output is still untrusted patch data for the
   push job (it runs in the job that ran PR code).

## Task T3 — `lockfix: gradle-verify` template and rollout support

1. New stub template `templates/dependabot-lockfix-gradle-verify.yml`, modelled
   on `templates/dependabot-lockfix-gradle.yml`, calling the reusable with:
   - `java-version: "__JAVA_VERSION__"`
   - `lockfix-command`: first `./gradlew kotlinUpgradeYarnLock`, then
     `./gradlew --write-verification-metadata sha256 --continue
     __LOCKFIX_GRADLE_TASKS__ -x test -x check`. A failing build task after
     resolution must not stop the metadata from being packaged (a bump that
     breaks compilation should still get its checksums, so CI shows the real
     error) — decide how (e.g. capture the exit, `::warning::`, exit 0) and
     test it.
   - `commit-paths: gradle/verification-metadata.xml kotlin-js-store/yarn.lock`
   - `append-only-paths: gradle/verification-metadata.xml`
   - `host-tool-checksums: true`
   - `commit-message: "fix(deps): regenerate Gradle verification metadata after dependabot bump"`
   - header comment explaining the stub, in the existing templates' style.
2. `scripts/rollout.sh`: accept `lockfix: gradle-verify` (it already renders
   `dependabot-lockfix-$LOCKFIX.yml`), add a fleet key `lockfix_gradle_tasks`
   (default `""` in `fleet.json`'s defaults block) rendered into
   `__LOCKFIX_GRADLE_TASKS__` via the existing `sed_escape` render path. Hard
   error, like the script's other hard errors, when `lockfix` is
   `gradle-verify` and `lockfix_gradle_tasks` is empty, or when
   `lockfix_gradle_tasks` is set with any other `lockfix` value. Repos without
   the key must render byte-identically to today.
3. Tests in `scripts/rollout.test.sh` (new lettered cases in its existing style,
   with a fixture repo in its fake fleet): the stub renders with the tasks
   substituted; the two hard errors; a repo without the key is unchanged.
4. README: document `lockfix: gradle-verify` and `lockfix_gradle_tasks` beside
   the existing lockfix section and the fleet-keys list, including that the
   task list should be every Gradle task CI runs on Linux plus any property
   that widens resolution (allotmint's `-Pallotmint.iosKlibs`).
